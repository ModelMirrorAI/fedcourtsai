# CLI reference (`fedcourts`)

`fedcourts` is a thin wrapper over the library, used by humans, scripts, and the
pipeline workflows. Run `uv run fedcourts --help` for the live listing, or
`uv run fedcourts <command> --help` for a command's flags; this page is the
grouped overview. `--version` prints the installed package version.

Commands fall into the groups headed below: **ingestion** (write the corpus),
**corpus inspection** (read it), **validation** (the gate), **corpus
transport** (move the blob), **diagnostics**
(read-only probes), **metrics & reporting**, **agent support** (fan-out
matrices and registries), **maintenance** (corpus-informed cleanup), and
**local iteration**. For the design behind the
corpus/ledger split see [data-pipeline.md](data-pipeline.md); for how the
workflows wire these together see [pipeline.md](pipeline.md).

Where a command writes a roll-up under `metrics/`, the path is relative to the
configured metrics root and `--out`/`--json` overrides it.

## Ingestion — write the corpus

Onboard and refresh raw facts. `pull`/`discover`/`pull-all`/`enrich-opinions` use
the rate-limited CourtListener **REST API** (need an API token); `live-poll`,
`historical-terms` and `refresh-dockets` use the **supremecourt.gov docket
JSON** (no token, no
budget — the SCOTUS live channel, [live-sources.md](live-sources.md)). All
ingest through the same core, so the corpus is written identically. `make-fixture-corpus` is the
odd one out: it writes a tiny **synthetic** corpus from hard-coded facts (no
source, no network) for offline local runs and tests, never a substitute for the
real corpus.

| `pull` | Onboard or refresh one docket from the REST API and report whether it changed (the first pull onboards). | `--court`, `--docket` |
| `refresh-historical` | Re-open past Terms for a full historical re-walk: clears the per-(Term, stream) walk cursors so the next `historical-terms` invocations re-cover them from the numbering base. Moves no data and fetches nothing itself. For when the pipeline learns to read something the walk did not capture — a new column, a corrected parser, a disposition pattern that used to be missed — since a Term at its frontier is otherwise invisible to every later run. Re-walking **adds rows**: re-served dockets upsert onto their existing rows through the corpus latches, so no row is deleted and `case_id` never moves — but an *unlatched column* takes the fresh parse, and the cert-stage disposition and its dates are unlatched, so a tightened pattern also **retracts** a stale reading. That is the way back from a false positive on a docket no rotation revisits — a denied, dismissed or terminated row has left both rotations, and a granted one leaves the live rotation once no unresolved event remains on it — and it works only while the corrected parse still reads *some* disposition, since a record that now reads undecided is counted `skipped_undecided` and never ingested at all. | `refresh-dockets` | Re-snapshot **named** SCOTUS dockets without re-walking their Terms — the targeted counterpart to `refresh-historical`, for when the rows needing a fresh read are known and enumerated rather than a whole population, and re-covering a Term would pay for its entire serial range at ~1 req/s to reach a handful of them. The Term's end is `--end-misses` (default 10) consecutive misses past the highest serial the corpus already stores for it; a miss below that serial is a withheld number, listed. A Term before the live floor (`live.term_floor_year`) or at or after the current docket Term is refused; the current Term's stream is frontier discovery's. An apply for a Term outside `REGISTERED_APPLY_TERMS` (OT2024 only) is refused: each Term's apply moves the interim base rate by its own amount and needs its own freeze-record entry first. Exits 1 on a refusal, a fetch failure or a missing corpus; 2 on an apply with no `--max-rows`, with `--cache-dir` or for an unregistered Term, on an unreachable Term, or on a non-positive `--end-misses`, `--limit`, `--max-rows` or `--max-run-seconds`. The apply is a corpus write that moves the interim base-rate population, so it runs on run-repair's `application-backfill` pass after the long-conference release ([data-pipeline.md](data-pipeline.md#maintenance-passes)); a dev checkout over a pulled corpus produces the dry run. **Credential split** (run-repair runs the pass as three jobs; versioned pydantic files in `src/fedcourtsai/handoff.py` and `pipeline/application_backfill.py`): `--emit-corpus-projection PATH` writes each Term's highest stored serial and live-owned serials, fetching nothing; `--projection PATH --plan-out PATH` walks against that projection with no corpus and writes each served docket JSON verbatim with the walk's ledger — identity, ownership by identity and the prediction guard need the corpus, so the ledger counts those rows as `unresolved=N` and its "would land N" is an upper bound (`--plan-out` without `--projection` exits 2); it prints the ledger, then writes the plan only if the walk reached no fetch failure and the plan passes the same whole-plan check `--from-plan` runs, else exits 1 with no file; `--from-plan PATH` needs the corpus and fetches nothing: it refuses a plan whole (exit 1) on a record served under another number, an unlisted, duplicated or missing record, a resolved case id, a record not shaped as a supremecourt.gov docket JSON (a top-level key outside the served set, no `CaseNumber` string or `ProceedingsandOrder` list), a planned row whose fields are not what its record maps to, a fetch-failure note, or a held note other than the served-number check's — the PII carve-out in `docs/data-sources.md` admits served docket JSON and its parsed fields, nothing else — then re-reads ownership, resolves identity and applies the prediction guard against the corpus, and with `--apply --max-rows` lands the rows under the same short-walk and bound refusals. Dry-run by default. | `--term` (repeatable), `--apply`, `--max-rows`, `--end-misses`, `--limit`, `--max-run-seconds`, `--cache-dir`, `--out`, `--emit-corpus-projection`, `--projection`, `--plan-out`, `--from-plan` |
| `historical-terms` | Load one capped chunk of the historical per-Term set through the live channel: walk the configured October Terms' docket serials sequentially (persisted per-(Term, stream) cursors, so runs resume) and ingest **every decided petition**, denials included. `refresh-historical` clears those cursors when the pipeline learns to read something the walk did not capture, so past Terms can be re-walked. Ingested petitions land already resolved (label, snapshot, events, OT2021+ documents) and feed the statpack's per-Term base rates and replay/evaluation only; **writes no queue files**. The `run-seed` workflow loops it, passing the budget still remaining as `--max-run-seconds` so the final chunk stops itself before the job's hard timeout. | `--report`, `--totals`, `--max-probes`, `--max-run-seconds`, `--summary-out` |
| `discover` | Onboard newly-filed dockets in the tracked courts, advancing each court's watermark (dormant in production: `pull.discover_new_filings` is off — the live channel onboards SCOTUS filings). | `--since`, `--limit` |
| `pull-all` | Refresh the stalest tracked cases within the API budget; write the predict queue, the evaluate queue, and the unrecorded-outcome queue (decided but not deterministically recordable, surfaced on the window's Actions step summary). No queue starts anything: routing the predict queue stamps `predict_queued_at` — which the live channel's own re-queue reads as its daily debounce, and `run-predict`'s derivation reads only for ordering and as proof that provisioning ran, never as a same-day hold, since that derivation is the only lane that mints — and the count lands on the window's step summary. The evaluate queue carries this cycle's fresh resolutions **plus** the **backlog deriver**'s additions — owed gradings re-derived from ledger state (resolved + predicted + unevaluated); only the derived cases are capped by `evaluate.backlog_cases_per_cycle`. Nothing consumes that file as a trigger and no `evaluate_queued_at` stamp is written: it is reported as a count only, since `run-evaluate`'s own scheduled derivation re-derives the same backlog itself; it also holds off a case stamped today, so a pull-window stamp would rotate owed gradings away from the only lane that grades them. | `--limit`, `--out`, `--evaluate-out`, `--unrecorded-out` |
| `live-poll` | One SCOTUS live-channel cycle: probe the Term's docket-number frontier across the paid, IFP, and application numbering streams, onboarding new petitions and applications (persisted per-(Term, stream) cursors) — and, for `live.outgoing_term_grace_days` after the July roll, the outgoing Term from its own cursor so its late tail is caught before the historical walker loses it, re-poll the live watchlist — pending petitions (distributed first, nearest conference first; then recent Terms) plus granted dockets retained on their open merits event until judgment, minted at cert-grant detection (see `docs/data-pipeline.md`), with any polled docket unpolled past `live.max_poll_staleness_days` leading the cycle ahead of both, stalest first, up to `live.max_overdue_per_run` a cycle (a never-polled row is never overdue), re-poll unresolved interim applications (capped at `live.max_applications_per_run`; a changed, still-unresolved substantive application in scope queues predict, daily-debounced — escalation signals latched to the corpus either way), detect resolution from the proceedings text, and write the same three queues as `pull-all` — with predict queued on **distribution transitions** (fresh distribution or relist) of gate-admitted petitions, the cert-calendar predict trigger. After the polls, a bounded, failure-isolated ledger-outcome convergence records every salience-selected moment the corpus closed without a ledger `outcome.json` — decided in the last 90 days, or at any age where the case holds a prediction at that stage — resolving its open sibling moments from the same disposition, and prints its counts (see *Ledger-outcome convergence* in `docs/data-pipeline.md`). The cycle ends with the salience gate's selection pass and its bounded sweep of the petitions the transition trigger missed — the selected ones, plus a deferred case re-admitted to finish an existing predictor cohort, narrowed to that cohort's events (see `docs/salience.md`). Last, the **document-freshness** pass checks every predict-relevant case the two rotations polled and did not provision on a trigger: where the stored documents lack a link the docket just read now selects — an opposition, reply, invited brief or merits filing docketed since the case was provisioned, a respondent's brief lost at an earlier fetch, an application's response or reply — it provisions the case through the poller's own fetch, idempotent per kind and URL, so an unchanged link is never re-downloaded; moved dockets first, at most `live.document_freshness_per_run` cases a cycle (0 disables it), and a case past the cap or the deadline is owed again at its next poll; it runs on what the polls, the convergence and the sweep left of the soft deadline, and is failure-isolated like the convergence. It prints a `Document freshness:` ledger line (candidates, checked, stale, refreshed — cases attempted, failures included — documents, unwritten, failed, deferred, unchecked, and the owed kinds; `error=<type>` where the pass itself raised) — see *Document freshness* in `docs/live-sources.md`. Closes with the window's document-fetch losses by reason, zero-filled (`bio-partial` among them — a stored opposition row short of the briefs the docket nominated); a window that lost anything also emits a `::warning::` and a block on the Actions step summary, which is the surface that outlives the run log. | `--term`, `--limit`, `--max-run-seconds`, `--out`, `--evaluate-out`, `--unrecorded-out` |
| `enrich-opinions` | Fill the **cert-granted SCOTUS slice**'s reporter cites and opinion bodies from REST: over the rows carrying `date_cert_granted` and not yet an opinion (`has_opinion` is the idempotency key, so a converged corpus spends nothing), resolve each case's published opinion cluster by either of two routes — the docket's own `clusters` links (from the newest stored snapshot where that one is REST-shaped, else a docket fetch) and, where those are empty, the clusters upstream joins to the case's court and docket number, since the id a granted row carries is its cert-stage docket and the merits cluster commonly hangs on a sibling docket row for the same number; a list result carries the whole cluster serialization, so that route needs no follow-up fetch, and a row with no docket number stops at the first route — take the cluster's reporter `citations` and `citation_count`, and take the cluster's first sub-opinion's `plain_text` as the body. The row is written through the corpus's own upsert, per case as it converges (casestore mirror included), which is what lets `has_opinion` derive and `query --full` hydrate the body; a direct `UPDATE` would break the freshness invariant `casestore.read_opinion_text` rests on. Because `has_opinion` latches, a wrong body is permanent, so the pass **refuses rather than guesses**: several candidate clusters — linked on the docket, or matching the number — are skipped, a resolved cluster must not name a docket other than the one it was reached from on the docket route and, on the number route, a docket the pass fetches and finds to be in this court carrying this number (upstream's filter is not the test, because `has_opinion` latches), and an opinion whose upstream `type` marks it a separate writing (a concurrence, a dissent) never becomes the body — each counted, and only the separate-writing refusal still lands the citations. A stored hyperlink is never fetched as given: a link must resolve under the client's own REST base and name `<resource>/<numeric id>/`, and only the id reaches the client. Four requests a case resolved by docket number (the docket, the cluster list, the docket that cluster names, the opinion) — three where that cluster already names the case's own docket, which owes no identity fetch — and three by the docket route (two where a REST-shaped snapshot already links the cluster), with a case neither route resolves stopping at two, so `--max-cases` bounds the run's spend ahead of the rate governor, and an exhausted API budget — or a 429 the client's retries could not clear, a quota wall whichever window imposed it — stops the walk cleanly, deferring the cases it did not complete for a re-run in a genuine dead zone; a per-case REST or parse failure is recorded and the walk continues. A granted row whose docket id is the live channel's reserved-range mint addresses nothing upstream, so it is reported `live_only` rather than walked. A no-cluster case is retried on the next run — which is how a grant picks up its opinion the run after publication — so two populations are permanent residue: a grant that never publishes an opinion (a GVR, a DIG), and a decided grant neither route resolves (no docket number to ask with, or a number upstream joins several clusters to). The walk therefore takes the **git ledger's decided merits cases first** — a case whose `data/cases/<court>/<docket>/events/` already holds a committed merits event (a declared merits moment, per `pipeline/moments.py`) **and** whose `merits_judgment` has latched — because grading a merits forecast is the only thing the body is an input to, and `case_id` order puts those few dozen cases *last*: upstream mints a current-Term grant one of the highest docket ids there is, so the case the pipeline is waiting on would sit dozens of capped dispatches behind decade-old grants. A *pending* ledger case is deliberately left in the rotation: its opinion does not exist yet, and the promoted group is walked in full, so promoting it would spend the whole `--max-cases` on guaranteed `no_cluster` verdicts and stall the backlog until those cases are decided — it is promoted at the latch instead, which the live poll writes within a day of the decision, and the promoted group stays smaller than the cap because a decided case converges and drops out where a pending one never would. Within each of those groups it rotates on a **last-attempted cursor** rather than walking `case_id` order: an applied run stamps `opinion_enrich_attempted_at` on every case it classifies — a landed body, no cluster, a refusal, a 4xx on one of its records — through the same upsert the enrichment itself writes through, and candidates are taken never-attempted first (in `case_id` order), then oldest stamp first, so the residue rotates to the back and successive runs advance through the slice instead of re-spending on one head. What stamps is what upstream answered *about the case*: a 5xx, a transport failure, an unparseable body, or a 4xx on a collection query (the question refused, not the case) is not, so that case keeps its place, as does a case the run never reached — deferred behind a wall, or past `--max-cases`; a dry run stamps nothing, so it reports what the next applied run would walk. The run reports `promoted`, how much of the cap that group took, since the walk takes it in full and the backlog advances only on what is left. `--case <court>/<docket>` (repeatable) narrows the walk to named cases — a **diagnostic**, not a second way into production: the applied lane is the dispatched enrich job, which names no case, and a dev checkout's corpus role is read-only, so a local `--apply` cannot be pushed. It answers what one case costs and where it stops (which route reaches its cluster, whether the cluster is ambiguous, whether the opinion carries text) without spending a slice to find out; it narrows only — the same eligibility predicate decides and `--max-cases` still bounds — and a named case the predicate does not admit is reported in `ineligible` with the reason rather than silently skipped, since a run that said nothing about a case the caller named is the one failure mode naming it exists to rule out. Operator-run where the corpus is pulled, `corpus-push` after an `--apply`; it is dispatched rather than scheduled so an operator sizes and times each run against the shared REST budget, and run outside a pull window because the rate governor is per-process. Dry-run by default — the requests are spent either way, so the dry run is how the spend is inspected. Prints an `OpinionEnrichmentResult`. | `--apply`, `--max-cases`, `--case` |
| `make-fixture-corpus` | Build a tiny deterministic synthetic corpus (cases/events/snapshots across several courts) so the read commands work offline, no remote. | `--out` |

`--limit` / `--max-probes` / `--max-run-seconds` may only *lower* the per-run cap
from `config/`, never raise it, so a run provably stays within budget. The one
exception is `enrich-opinions --max-cases`, which has no `config/` counterpart
and *is* the cap: the pass is operator-run rather than scheduled, so its bound
is set at the call site by whoever is watching the spend.

## Corpus inspection — read the corpus

Read-only views. They read the pulled file by default, without ever changing
its bytes: a blob older than the reading code's schema is read through a
migrated temporary copy rather than migrated in place, so it keeps matching
its pointer (see *The ranged read backend and the blob's physical layout* in
[data-pipeline.md](data-pipeline.md)). Where
`--corpus-backend` is listed, `ranged` queries the immutable blob in place on
the corpus remote instead (per-query egress in KBs, read stats echoed to stderr;
see *The ranged read backend* in [data-pipeline.md](data-pipeline.md)).
`query` and `open-events` additionally accept `service` — forward the request
to a `corpus-serve` sidecar (needs `FEDCOURTS_CORPUS_SERVICE_URL`) so the
calling shell holds no cloud credentials; same rows, and `query` prints the
same read-stats line
(see *The corpus query sidecar* in [data-pipeline.md](data-pipeline.md)). The
provisioning commands (`provision-snapshot`, `materialize-event`) additionally
accept `casestore` — read the case's snapshot/documents/event from the per-case
content store rather than the corpus blob (needs the store configured).
`provision-opinion` does not, though it writes into the same `record/` tree:
the presence bit and the citation it stages are index facts and the content
store exposes no rows, so it reads the row over `local`/`ranged` while the
body half routes itself to whichever half of the estate holds it.
Under the corpus-split mode — an environment with a content store, where the
payloads live only there — `provision-snapshot` and `materialize-event` default to `casestore`
without the explicit flag, so the whole fleet reads one store from one setting.

| Command | Purpose | Key flags |
|---------|---------|-----------|
| `corpus-info` | Show the packed corpus location, row count, snapshot count, and a `freshness:` line — the newest `last_pulled` over the cases and the newest stored snapshot date. Under `local` it opens the pulled blob strictly read-only and runs no schema migration, so the report never changes the file it reports on and the blob keeps matching its pointer. When the out-of-band pointer override is set, a `pointer:` line follows the freshness line: under `ranged` it names the override's digest (the blob the read actually served), under any other backend it says the override was set but not read — so no vintage is quoted blind against the wrong blob. Three more `pointer:` lines guard the same claim. Under `local`, one says when the blob on disk was pulled from another pointer than the committed ref (the pull sidecar names a different digest), and one says when the bytes on disk no longer match the sha256 their pointer names — the pull sidecar's, else the committed ref's — which is what a writer or maintenance command run against it locally leaves behind, its default dry run included, since it opens the file through the writer seam (the read-only commands never rewrite it): a blob untouched since its pull is settled from the sidecar's timestamp, anything else by hashing the blob (seconds over the full corpus). With no override set, under either backend, the last says when the checkout's committed pointer differs from the one `origin/main` carries as of the clone's last fetch (read from the local object store, no network; silent where `origin/main` was never fetched), so a checkout on an old commit — or a branch off `staging` between syncs, since data commits land on `main` only — does not quote an old blob's vintage as current. To read production's blob from such a checkout, read ranged with `git show origin/main:corpus/corpus.db.ref` supplied as the out-of-band override: the `local` backend never consults the override, and a local pull through it leaves a blob the first of these lines then reports as not the committed ref's. The committed pointer is a content digest with no date, so this is the cheapest surface that says how old the blob on disk is: the docket pack computes the same `last_pulled` maximum for its `pulled through` line, but only as part of building a pack. A payload-free index reports `no snapshots in this blob` — the snapshots are in the per-case content store, which the snapshot count does not read — and is read on its pull date alone. `--text-coverage` adds the other property worth knowing before quoting a blob — whether its documents carry text at all: over the live-channel SCOTUS rows (the only channel that stores documents) it counts the stored petitions, applications, responses to applications and applicants' replies, separately linked appendices, cert-stage briefs in opposition, cert-stage replies, invited briefs of the Solicitor General, per-side merits briefs and merits replies, and derived questions-presented rows whose text is empty or whitespace-only, exactly what provisioning stamps on the cell manifest as `empty_text` — written into the cell's manifest, never into a corpus column, so the share has to be counted rather than queried. It is the one read on this command that reaches the content store. The counts stay **per kind** and are never pooled into one total, because emptiness has three causes: on the fetched PDFs it is a scanned filing with no text layer; on the four merits kinds a near-zero count is the shape of the granted slice rather than a coverage gap, since nothing selects them before a grant — and the two reply rows are narrower again, bounded by the granted cases whose docket carries a reply at all; and an empty derived questions-presented row is as likely to be a capture the deriver would not vouch for over a petition that does carry text (and, since a row is written only where the petition has text, that column is structurally unable to carry a scan — the report says so). Four header lines, each self-limiting, in this order. `text source:` comes **first**, naming the blob's own tables or the per-case content store: every line under it asserts an absence, and a blob-only read of a split corpus finds no documents at all, so the provenance has to be read before the counts. Then `text coverage:`, leading with the **petition** count and share, split into the scans OCR would repair and the PDFs the extractor could not open at all, which it would not; `missing documents:`, the larger failure mode beside it — the cases holding no petition row, over both the stock of distributed cases and the narrower set queued or predicted, which no extraction fix reaches; and `text frame:`, the pass's reach as a bare count, explicitly not a failure rate, since most of the walked slice was never fetched for. The **queued** count is keyed on the docket form's own primary document: a cert-form row is measured against its petition, an application-form row against its `application` — the filing that opens one — and the second is counted on an indented line under `missing documents:` rather than pooled in, since a docket reported as missing a filing the Court never expected it to hold is a repair aimed at nothing. Neither count is a floor: an application docket holding its application is as complete as a cert docket holding its petition, so the indented count drains as the documents store — which is why each gap prints against **its own form's denominator** (the queued cert-form rows, the queued application-form rows, which partition the queued set), since a number that drains is unreadable against a population it is not a gap over. That queued set is read over both minting lanes — the rows carrying the pull/live lane's `predict_queued_at` stamp, plus the cases the git ledger holds a committed prediction for, which is all a stamp-free scheduled derivation leaves — so it is the git ledger, not the corpus alone, that the denominator is taken over: on the stamp alone it would shrink selectively as the scheduled lane takes over, dropping exactly the rows no lane stamped. The wide distributed count stays petition-keyed and unfiltered, so it keeps the application rows entirely. The `petition` kind itself spans the family, and the coverage line says so where the figure is printed rather than leaving it to this row. Then the sixteen zero-filled `kind` x `segment` cuts (the salience gate's scored segment — in practice paid against IFP — against the rest of the live slice) and **three** untruncated case-id ledgers: `empty text`, what read back empty and by which kind, and `no petition, queued` / `no application, queued`, each docket form's queued rows holding no primary document. All are enumerated for the same reason: the repair is a per-case question — for the last two, which of the provisioning routes a given case missed — and a count names no case. Opt-in and not cheap: it walks the documents of every live-slice case, tens of thousands of rows, which under the split is a content-store manifest round trip each plus a full text body per stored document — taken on a bounded pool of parallel readers, the same one the questions-presented backfill uses — so the default vintage report stays a few KB. ## Corpus transport — move the blob, and copy a slice of both stores

The pull/push pair the data workflows (and a developer with credentials) use to
move the corpus index blob between disk and the S3 remote; both resolve the
remote from the environment's corpus base URL — one address per environment,
with the index and content-store segments derived in `fedcourtsai.paths` — or
from an index-remote URL named on its own (legacy `DVC_*` spellings accepted).
The seeder
below moves a *slice* of both stores onto a second, non-production pair, and
names its source **and** its destinations explicitly rather than reading
either from the environment — the pinned source is what it refuses to write to.

| Command | Purpose | Key flags |
|---------|---------|-----------|
| `corpus-pull` | Download the blob the pointer the read paths resolve names — the out-of-band override when set, else the committed `corpus/corpus.db.ref` — verifying its checksum + size before the file lands. `--missing-pointer` governs only the committed file, so it is inert while the override is set. Every pull records the resolved pointer in a gitignored sidecar beside the blob, which is how `corpus-info` flags a blob on disk that is not the committed ref's. Before downloading it warns on stderr, without changing what it fetches, when the local blob it is about to replace no longer matched its pointer (a writer or maintenance command, or its dry run, rewrote it) and, when the committed pointer is the one resolved, when that pointer differs from `origin/main`'s as last fetched. | `--missing-pointer fail\|warn` |
| `corpus-push` | Digest the local blob, upload it to its content-addressed key (put-if-absent; the remote stays add-only), and rewrite the pointer — blob before pointer, so a committed pointer always resolves. Refuses to run while the out-of-band pointer override is set: a writer owns the committed pointer. | |
| `corpus-seed-slice` | Copy a named docket slice into a **staging corpus** — its own bucket/prefix pair, so orchestration and the read/write seams get live end-to-end verification without anything gaining write access to production. Builds the two halves a split-mode corpus has: a payload-free index blob carrying only the slice's `cases` and `events` rows (rebuilt through the corpus's own upsert seams, so it is schema-current whatever the source's vintage; the opinion body is dropped and no snapshot or document row is written, so the slice has split-on parity whatever mode the seeding process runs under) published to `--dest-remote` at its content-addressed key exactly as `corpus-push` publishes production's, and a **key-level copy** of every content-store object under each case's prefix into `--dest-casestore` — the writers' own bytes, not a re-serialization, so every dated snapshot and content-addressed document leaf arrives unchanged. Objects are copied *before* the blob is published, so a reader resolving the new pointer always finds the payloads its rows refer to; within a case the documents manifest lands *after* the leaves it names, the same rule one level down. The store's two kinds of object are copied on different rules, and the distinction is load-bearing: write-once keys (dated snapshots, content-addressed leaves) the destination already holds are skipped, while the three **mutable** manifests the writers overwrite in place (`case.json`, `events.json`, `documents/documents.json`) are re-copied every apply — skipping those would leave a re-seeded staging store describing a case the source has moved past, its manifest naming a superseded filing while the blob half, rebuilt from scratch each time, says otherwise. Each side is named as **one base URL** (`--source-base-url` / `--dest-base-url`), from which both store halves derive, or as its two halves individually — never a mix, since a base and a half that disagree name two different stores. The source is **pinned at the invocation** — never resolved from the environment, so a repointed shell or Actions environment moves neither what the seeder reads nor what its rail compares against; the ranged backend resolves the checkout's committed pointer against the pinned remote (no pull — a bounded slice is point lookups), both halves read-only. **The rails, and what they are second to:** IAM is the guarantee — the seeding role is read-only on the production stores — and the command refuses, before anything is read, a corpus pointer override anywhere in its environment (the index half of the self-seeding hazard — a staging-flipped dev shell may carry one), a destination that *is* either pinned source store (compared as `(bucket, prefix)` through the transports' own parsers, so no spelling slips past) **or sits inside either source bucket at any prefix**, plus a `--stage-db` that would clobber the committed corpus pointer. Idempotent (the remote is content-addressed and add-only; write-once keys already present are skipped), and bounded by `--max-cases`. Dry-run by default, printing the per-case census — rows, events, snapshots, documents, objects, and (on a ranged read) the source index blob's resolved key and size, the pin's value at this run and where a stale source pin becomes visible — which is the reading an apply is dispatched on; an apply additionally reports what it copied and **the published pointer**, the one thing a staging consumer needs and the thrown-away runner would otherwise lose. Runs only in the `staging-corpus-refresh` workflow, the one reviewed asker of the staging read-write role (whose trust names the `staging` environment itself); a dev checkout can dry-run it against the read-only role. Provisioning the stores, the variables, and the role is the maintainer runbook in [security.md](security.md). | `--source-base-url`, `--dest-base-url` (or `--source-remote`, `--source-casestore`, `--dest-remote`, `--dest-casestore`), `--dockets`, `--dockets-file`, `--apply`, `--max-cases`, `--stage-db`, `--summary-out` |

| `predict-matrix` | Emit the predictor × case × event GitHub Actions matrix as compact JSON. **Two input modes.** `--body-file` takes an explicit case list (one `{court, docket, events}` object or an array of them) and `--court`/`--docket` name one ad hoc; given no input at all, they come from the corpus-level **predict backlog** — every SCOTUS case with an open forecastable event that is in predict scope, **funded** (salience-selected, or carrying an open merits event, or already holding a committed prediction somewhere — cohort completion, with the claimable-board test applied as the narrowing below, which governs the never-predicted arm alone: the re-predict rule below is asked over the case's whole forecastable set), and missing at least one enabled predictor's prediction — capped per `tracking.yaml`'s `salience.sweep_cases_per_cycle` (the live sweep's own per-cycle cap, since the two select from the same population and a second ceiling could only promise cells the sweep's rate cannot feed) and `predict.max_attempts_per_cell`, so a scheduled or dispatched run derives its own work with no case list named. **Owing is not minting.** Three further conditions gate whether an owed case is minted *this* cycle, and all three are **holds** that clear as another lane advances, never exclusions. **Record freshness**: the case must have been observed by either ingestion channel (`last_live_polled` or `last_pulled`, whichever is fresher) within `BACKLOG_MAX_POLL_AGE_DAYS` = 7. The live sweep re-polls each candidate before queueing it and diverts a now-decided docket; a scan over committed state cannot, so the record's own age is its only guard against a forward cell on a case whose answer is already public. The hold clears at the case's next poll — the live windows poll four times a day on a stalest-first rotation. **Provisioning attempted**: the case must hold stored documents *or* carry a `predict_queued_at` stamp. The stamp is the pull lane's own record that it queued the case and the sweep provisions at queue time, so a stamp proves provisioning **ran**, whatever it found; only the never-queued-and-unstored class is held, and that class is genuinely timing-only. Reading document *presence* as the rule instead would conflate "not yet provisioned" with "provisioned, found nothing" and permanently bar every docket with no document route at all — `select_documents` has no application branch, so the whole interim lane would be excluded rather than held. An admitted case whose store came up empty mints a cell with a thin `record/`; that is the queued-without-petition coverage metric's problem to report, not this predicate's to exclude. **Outcome not disclosed**: per owed event, the case's newest stored snapshot must not already show that event's outcome, by the same textual scan provisioning refuses a forward cell on (`forward_leakage`); an event it flags is dropped and named on stderr with the entry that tripped the scan, and a case left with none is held. The live routing diverts such a decided-looking docket without recording why, and provisioning would refuse the cell anyway — but only after a round had spent a runner on it, and at every round until the event resolves or a newer snapshot stops disclosing it; a scan false positive therefore stays held until the docket itself moves, and its stderr line is how it is found. All three holds are **counted on stderr** with their reason, and every count is taken over the **owed** population alone — a case the owed check would drop anyway is not counted as held, or the figure would not mean what its sentence says. They are also **censored by the cycle cap** (the scan stops there; candidates past the break are in no figure), and the summary line says so when that happened. run-pull stays the sole provisioner, and the property that gives is a **throughput bound, not a latency one**: this backlog can never outrun run-pull's provisioning rate — the sweep's per-window cap plus the other provisioning paths' own bounds — so a held set larger than a window's provisioning clears over as many windows as it takes rather than by the next one. The same stderr summary names **which store answered the provisioning probe** (the content store under the corpus split, the corpus blob otherwise), so a mis-addressed store shows up in the plan output rather than as an unexplained short fan-out. The derivation also **reconciles at case grain**: beside the admission walk it computes, from the leaf predicates alone (the scope latch, funding, `_row_in_predict_scope`, `forecastable_event_ids`) and never from the walk, the **universe** of SCOTUS cases with an open forecastable event that are in predict scope and funded, and every step of the walk that derives, holds or turns a case away files it under one bucket with its reason — `derived`, `held_stale` / `held_unswept` / `held_decided`, or `dropped_already_queued` / `dropped_excluded` / `dropped_not_funded` / `dropped_owed_nothing` (every cell predicted or attempt-capped, or a cohort-only case whose narrowing left no claimable event) / `dropped_cap_reached`. The cap bucket is the censoring made explicit: candidates the walk never reached because it stopped at the cycle cap, and cases it reached past a full re-predict budget whose re-owed arm was therefore never asked, are filed there rather than left out. The summary line on stderr gives the buckets, and a `::warning::` names every universe case filed **nowhere** (unaccounted — owed work dropping out without a reason), filed **more than once**, or derived or held although the universe excludes it. A **closed** window's cells are not de-counted, so a supersession re-owes nothing: an event on which a closed window holds a counted cell stays covered. The two arms overlap per event and are disjoint per cell, so an event carrying both an engine with no cell and engines whose cells are all de-counted is owed on both and never mints one counted cell beside de-counted rivals. A re-predict **replaces** rather than adds: the older cell stays under its own run id, untouched, and the newest resolvable run per predictor — never a later window's cell where the predictor holds an earlier window's counted one — is the one provisioning stages and an evaluation names. ## Maintenance — corpus-informed cleanup

Deterministic sweeps that prune or converge already-merged derived artifacts the
append-only writers can never fix. All need a pulled corpus (`fedcourts
corpus-pull`), and they land through two channels, named by where the applied
result lands. The **maintainer-reviewed** sweep —
`cleanup-out-of-scope-predictions` — runs from a dev checkout, and a
maintainer lands the result as a **reviewed** (not auto-merged, manually
merged) PR on a `cleanup/*` branch. The **writer-lane** sweeps —
`reconcile-scope`, `dedupe-live-rows`,
`relabel-application-events`, `backfill-merits-judgments`,
`backfill-event-moments`, `backfill-merits-events`, the attribution
repairs `remove-unmintable-events` and `reopen-misattributed-outcomes`,
`converge-decision-dates`,
`scrub-bulk-cluster-fields`, and the fill sweeps
`normalize-docket-markings`, `backfill-response-fields` and
`backfill-decision-record` (in `--sweep` mode) — run
in run-seed's writer lane on its schedule, with a dry run from a dev checkout
available for inspection. What both channels share is why neither is a
collect commit: a destructive change to the ledger is a shape no collect
jail admits, so it lands either behind a maintainer's review or in the
writer lane's one pointer commit — atomic with the corpus it must match,
and bounded there by each repair's per-run blast-radius cap. The remaining
entries name their own channel.

Deliberate maintainer surface, never scheduled: run `dedupe-live-rows --apply` first (a merge takes the latch stickily from either twin), dry-run by default, run where the corpus is pulled, `corpus-push` after an `--apply`. A committed prediction on a cleared case stays committed **and graded** (the evaluate matrix never applies the salience skip). Prints a `SalienceUnlatchResult` — keep it: its untruncated cleared-id ledger, beside the pre-apply `corpus.db.ref` the command echoes, is the record of the pre-resize sticky set the write erases. | `--apply` |
| `caption-census` | The petitioner-class census: the salience gate's scored segment (live-slice, paid, modern-cert, resolved) cut by one registered caption rule (`pipeline.caption`) into federal / state / private, per Term and pooled, every cell with its `n` and grant-family rate. `--rule-version` names the rule (`caption-v1`, the default, or the widened `caption-v2`) and the result is stamped with it, so the two cut the same frame independently and a widening reads as a per-class, per-Term delta; an unregistered label exits non-zero rather than falling back. Deterministic and read-only — two runs over one corpus pointer agree byte for byte, which is what lets a statistical review of the run license a frozen selection constant (`docs/salience.md`) — the review of record for `caption-v1` froze the federal carve-in into sal-v2, the `caption-v2` review of record froze the widened carve-in into sal-v3, and the state class stays a reporting dimension only. Prints a `CaptionCensus`. | `--rule-version` |
| `distribution-census` | The distribution-parse census: two registered readings of the DISTRIBUTED phrase (`pipeline.cert_signals`) counted over one frame — the salience gate's scored segment (live-slice, paid, modern-cert, parseable Term) with **pending rows kept**, since the count is a banding input the gate reads long before a petition resolves and the ancillary-paper distributions the readings differ on accumulate on live pending dockets. Both counts come off each case's latest **live-shaped** snapshot — never the newest snapshot of either shape, since the entry-initial rule is a claim about the live channel's entry conventions and counting a REST payload's `docket_entries` under it would report a channel artifact as a parse delta; the corpus column supplies neither side (it holds one parse's answer, max-latched). The snapshot read is split-aware (`corpus.latest_live_snapshot` serves from the per-case content store under the corpus-split mode), so a split blob without the store wired reports the whole frame `unobservable` rather than failing — which is why the mode that dispatches it wires the store. Banded by one salience version's band function, so the reported delta — changed counts split by direction, the band-transition matrix, a per-Term rollup split by docket maturity, a per-band rollup keyed on the baseline parse's band, and every changed case id, complete rather than sampled — is attributable to the phrase-reading alone. The matrix is the **full band-by-band square, zero-filled**, so an observed zero is never an omitted cell; which half of it a parse pair can occupy is a property of the pair (a subset candidate can only lower the count, and every registered band function is monotone in it, so no case moves to a stronger band — `count_increased` observes the nesting on the frame read, the monotonicity is pinned over the scorer registry by test). A case with no live snapshot or no disclosed proceedings counts `unobservable`, never as agreement, and the stderr banner prints `cases` as a fraction of the `cases + unobservable` frame (or `no rows` where the frame is empty) and both pending denominators beside each other; pending is carried at both levels (`frame_pending` census-wide and per Term over the whole frame, `pending` per Term over the observable rows only); a subsampled frame row (`sample_weight != 1`) raises, as in `caption-census`, because every figure is a raw count. `--baseline-parse` names the incumbent reading and defaults to `DEFAULT_DISTRIBUTION_PARSE` — the one the corpus column holds, today the entry-anchored `dist-v2`; `--candidate-parse` is **required**, because the challenger is whatever a caller is arguing for and the registry cannot name it (defaulting it to a label would turn a bare invocation into a parse-against-itself census on the commit that activates that label). `dist-v1` is the entry-anywhere reading `sal-v1` through `sal-v3` were fitted on. `--version` names the band function; an unregistered label exits non-zero rather than falling back. Deterministic and read-only — it moves no band by itself. The `run-analytics` mode that dispatches it is in [pipeline.md](pipeline.md), and that job is where a census meant to be reviewed is produced: it uploads the JSON as a run artifact, so the reviewed file carries its own `corpus_sha256` rather than living only on a summary page. That artifact keeps the one-day retention every analytics run artifact does; the census is deterministic over the blob its `corpus_sha256` names, so re-reading it after the day is a re-dispatch, not a longer window. This is the **input-level** cut and its matrix is conditional on the corpus column being re-derived under the candidate parse (a latch-bypassing writer `UPDATE` — the upsert path max-latches the column, so a narrower count routed through it is a silent no-op); pinning a parse also needs a statpack rebuild and re-measured relist-tier rates, and the *selection* question is read from `salience-replay` with the candidate registered ([salience.md](salience.md)). Prints a `DistributionCensus`. | `--baseline-parse`, `--candidate-parse`, `--version` |
| `rederive-distribution-counts` | Re-derive the corpus `distribution_count` column under a registered distribution parse — the **first** of the three pieces of work that activate a new parse ([salience.md](salience.md)), and the one the `distribution-census` matrix is conditional on: until the column is genuinely re-derived, every downstream consumer (the gate's banding, the statpack's per-band base rates, the relist-tier cutpoints) is still reading the incumbent parse's counts. Over every **live-slice SCOTUS row** — where the column is populated, the bulk import having parsed no proceedings text — recount the conferences the case's latest **live-shaped** snapshot discloses (`corpus.latest_live_snapshot`, split-aware; the reads ride the shared bounded prefetch, so a slice in the tens of thousands costs a fan-out rather than a serial walk of GET latency) and write it with a **direct `UPDATE` that deliberately bypasses the upsert path's max latch**. The bypass is the command: the latch takes the larger of stored and incoming, so a narrower reading's every row is rejected, and the same write routed through `upsert_rows` would report success having changed nothing. What replaces the latch is **narrower** than the latch, and the difference is the operating procedure. A row with no live-shaped snapshot, or one disclosing no proceedings **entries** — an empty list as much as an absent key, since every live-polled docket carries at least its docketing entry — is counted `unobservable` and **left untouched**, never written to 0; a merely *truncated* entry list is not detectable here, where the latch would have rejected the regression whatever caused it. So **run the incumbent parse first**: that pass must report `changed = 0`, because the stored column is the incumbent reading of those same snapshots, and anything it moves is stored-column drift (a degraded payload, a dedupe merge-max, a backfill gap) rather than the reading — until it is zero, a candidate's changed set is a sum nothing can decompose. A row carrying **no stored count** is likewise reported and left alone rather than filled: the null is the parse-coverage sentinel for the whole live-signal family, so writing the count on its own would promote an unknown CVSG to an observed absence (`backfill-live-signals` owns them, and the interim application dockets the live channel keeps deliberately null sit there too). One pass **per invocation**, so a dry run and the apply inside one call cannot describe different work — across two dispatches the live channel intervenes, which is why the apply prints its own report — and the whole batch lands in one transaction. Idempotent: a converged column recomputes to itself. `--apply` refuses above `--max-changes`, printing the report first so the refusal is triageable; the default is sized off the measured delta (`dist-v2`: 378 rows of the ~22.7k live slice differ from their stored count, of which 181 sit in the census's narrower scored-segment frame — the census's own figure — while the incumbent parse moves 0), which makes it a guard against a catastrophic write rather than a wrong one; the sharper signal is `increased`, since under a narrowing parse a rise means the stored column sat below its own reading. Every figure is a raw row count, never denial-reweighted, and each carries its own denominator: changed and unobservable against the live slice, the band-move matrix against the **census frame** (paid, modern-cert, parseable Term) with that frame's own unreadable residue beside it, since a band label is only meaningful where the gate scores. The matrix is the full zero-filled square keyed on the band the **stored** column implies rather than on a second reading of the snapshot, so it need not agree cell for cell with `distribution-census`. The result carries the `corpus_sha256` it ran over — the ledger of a latch-bypassing write names the state it is re-derivable against. **Corpus-side only**: `data/` is never touched — a frozen `record/context.json` records the count the cell was handed, and rewriting it would retcon an information set. Note the durability limit: the live poll, `refresh-dockets`, and the Term walker's re-serve all upsert a count read under `cert_signals.DEFAULT_DISTRIBUTION_PARSE`, which the max latch takes where it is higher, so a re-served row reverts unless the ingest default moves to the same parse in the same batch. A **dispatch-only** run-repair pass (`repair=rederive-distribution-parse`, the label in `repair_target`, [pipeline.md](pipeline.md)), never scheduled: the parse a re-derivation runs under is a maintainer's decision read off a census. Run where the corpus is pulled; the dry run is available from a dev checkout. Prints a `DistributionRederiveResult`. Dry-run by default. | `--parse`, `--apply`, `--max-changes`, `--version` |
| `assert-cleanup-paths` | Enforce the **cleanup jail** on a change set (`git diff --name-status`): exit non-zero unless every change is a *delete* under a `data/cases/**/events/*/predictions/` subtree. The maintainer's sweep and the `cleanup-paths` CI check (on `cleanup/*` branches; review-time defense, deliberately not in the required list) both call it — the destructive counterpart to `assert-paths`. | `--name-status-file` |
| `assert-required-contexts` | Check a branch's **required status checks** against the jobs that can report them: exit non-zero naming any required context no workflow on that branch reliably reports (a matrix job, an expression-valued job name, and a trigger- or path-filtered workflow all count as unproduced — every unknown resolves that way, so the check can raise a false alarm but never bless a rule that hangs) (which would leave every PR into it pending forever — the auto-merging collect PRs first). `--candidate` reports, without failing, whether a context is safe to require yet. `scripts/promotion-gate.sh contexts` feeds it the live ruleset and `main`'s own workflows; see *Adding a required status check* in [pipeline.md](pipeline.md). | `--workflows`, `--context`, `--candidate`, `--base-branch` |

## Local iteration — the full cascade off Actions

`local-cascade` is the repeatable, local form of the "one full cascade proven"
milestone: it drives a single case through the whole derived-artifact pipeline —
**provision → predict → evaluate → validate** — without GitHub Actions, the
iteration loop that otherwise only runs inside `run-predict` / `run-evaluate`. It
reuses the production seams (the engine-runner, the predictor/evaluator
registries, the packed corpus, and `provision-snapshot`'s placement and record
writer) so a green local run faithfully predicts a green CI run.

| Command | Purpose | Key flags |
|---------|---------|-----------|
| `local-cascade` | Provision each cell's whole `record/` — the snapshot placed at its event's declared moment, the `context.json` freezing its mode and conditioning, and the documents cut with the snapshot, both staged copies through the contact-detail scrubs, through the same placement and record writer `provision-snapshot` uses — predict the event with every enabled predictor (`--predictor` narrows to one — the one-cell shape a token-spending smoke run wants), re-provision the way `run-evaluate` does (latest payload, no cut, `forward`: a judge grades a resolved event) and evaluate the resulting predictions with every enabled evaluator, then validate the produced ledger. Each predict cell's mode follows its event: `forward` for a pending one, `replay` where the corpus already marks it resolved — and both are placed at the moment their event declares wherever that moment has a dated trigger, the same rule `provision-snapshot` follows in either `--mode`. A cert petition baseline's opening date is docketing rather than the moment it declares, so a cascade replay cell on a resolved one takes no cut and reads the latest payload and every stored document, the disposing order included — the back-test's point-in-time provisioner is the lane that closes that. A cascade replay cell also gets no `DECIDED_BEFORE` clock, so its corpus priors are unmasked — the local loop's known narrowing against the back-test. The evaluate-half re-provisioning happens only where a ground truth was materialized. The output names the record left on disk (`snapshot:`, `context:`, `documents:`) and one `provisioned:` line per provisioning — role, event, mode, provenance, cutoff, document count — because the record on disk at the end is the last provisioning's. `--require-predictions` fails the run when no predictor cell wrote a prediction — a real agent that finishes blocked exits 0 with a validly-empty ledger, which a smoke must treat as failure. `--require-record` fails it, before any cell runs and so before any token is spent, when the corpus holds no snapshot for the case: such a cell runs with no snapshot, no context and no documents, and a smoke certifying the production cell posture must not pass over one. | `--court`, `--docket`, `--event`, `--engine`, `--run-id`, `--predictor`, `--corpus-backend`, `--require-predictions`, `--require-record` |

It reads the case from the packed corpus — point it at the synthetic fixture
(`make-fixture-corpus`) for a fully offline run, a real `corpus-pull`-provisioned
one, or (via the corpus-backend setting) the blob in place on the corpus remote.
`--corpus-backend` overrides that setting for the cascade's *own* provisioning
reads only (`local` or `ranged` — the query sidecar's `service` surface does not
serve them); the spawned agent still inherits the ambient corpus settings, so an
environment configured for the sidecar drives the agent's retrieval through it
while provisioning reads the blob directly — the split the `integration-test`
workflow's engine-smoke scenario runs on.
With no `--event` it runs every event the case defines; a resolved event also
gets its ground-truth `outcome.json` materialized so the evaluate stage has
something to score. The derived artifacts land under `data/` exactly as a real run
would — **review and discard them**, don't commit a local cascade's output.

**Engines.** `--engine` selects the backend for every cell:

- `stub` (default) — the deterministic, offline, token-free reference engine.
  This is the acceptance path: valid artifacts end to end with no network.
- `replay` — also offline, but emits a **captured real prediction** from the
  cassette at `FEDCOURTS_REPLAY_ROOT` (a committed recording under `tests/cassettes`)
  instead of the stub's trivial floor. The recorded forecast carries a real
  probability and panel votes, so the scoring metrics and leaderboard roll-up run
  over realistic output; identity fields are rebound to each cell. Set
  `FEDCOURTS_REPLAY_ROOT` or the command errors clearly.
- `claude-code` / `codex` / `gemini` — drive the **real** headless agents
  (`claude`, `codex`, `gemini`) over the same cell contract the workflows use
  (the inline-identifier kickoff prompt plus the env vars), so the cells are
  byte-identical in shape to a CI run. The `claude` CLI ships in the devcontainer
  (`codex` you install yourself; `gemini` is `npm install`-ed, as the workflow
  does).

**Auth for the real engines.** Credentials are inherited from the environment,
never assembled by the command. For Claude, set either:

- `ANTHROPIC_API_KEY` — pay-per-token, exactly as CI meters automated inference; or
- `CLAUDE_CODE_OAUTH_TOKEN` — the **subscription** OAuth token from
  `claude setup-token`, so local iteration draws on your Claude subscription
  instead of billing per token. This mirrors the `claude_code_oauth_token` fallback
  noted in `run-predict.yml`.

For Codex, set `OPENAI_API_KEY`. The pinned codex CLI never reads that
variable itself, so the runner feeds it to `codex login --with-api-key`
(over stdin) before each cell — into a run-scoped temp `CODEX_HOME`, so your
`~/.codex` subscription login is never touched; unset the variable to use an
existing `codex login` instead, and an explicitly exported `CODEX_HOME` wins
over the run-scoped default. For Gemini, set `GEMINI_API_KEY`.
