# CLI reference (`fedcourts`)

`fedcourts` is a thin wrapper over the library, used by humans, scripts, and the
pipeline workflows. Run `uv run fedcourts --help` for the live listing, or
`uv run fedcourts <command> --help` for a command's flags; this page is the
grouped overview. `--version` prints the installed package version.

Commands fall into the groups headed below: **ingestion** (write the corpus),
**corpus inspection** (read it), **validation** (the gate), **corpus
transport** (move the blob), **diagnostics**
(read-only probes), **metrics & reporting**, **agent support** (fan-out
matrices and registries), **maintenance** (corpus-informed cleanup), and
**local iteration**. For the design behind the
corpus/ledger split see [data-pipeline.md](data-pipeline.md); for how the
workflows wire these together see [pipeline.md](pipeline.md).

Where a command writes a roll-up under `metrics/`, the path is relative to the
configured metrics root and `--out`/`--json` overrides it.

## Ingestion — write the corpus

Onboard and refresh raw facts. `pull`/`discover`/`pull-all`/`enrich-opinions` use
the rate-limited CourtListener **REST API** (need an API token); `live-poll` and
`historical-terms` use the **supremecourt.gov docket JSON** (no token, no
budget — the SCOTUS live channel, [live-sources.md](live-sources.md)). All
ingest through the same core, so the corpus is written identically. `make-fixture-corpus` is the
odd one out: it writes a tiny **synthetic** corpus from hard-coded facts (no
source, no network) for offline local runs and tests, never a substitute for the
real corpus.

| Command | Purpose | Key flags |
|---------|---------|-----------|
| `pull` | Onboard or refresh one docket from the REST API and report whether it changed (the first pull onboards). | `--court`, `--docket` |
| `refresh-historical` | Re-open past Terms for a full historical re-walk: clears the per-(Term, stream) walk cursors so the next `historical-terms` invocations re-cover them from the numbering base. Moves no data and fetches nothing itself. For when the pipeline learns to read something the walk did not capture — a new column, a corrected parser, a disposition pattern that used to be missed — since a Term at its frontier is otherwise invisible to every later run. Re-walking **adds rows**: re-served dockets upsert onto their existing rows through the corpus latches, so no row is deleted and `case_id` never moves — but an *unlatched column* takes the fresh parse, and the cert-stage disposition and its dates are unlatched, so a tightened pattern also **retracts** a stale reading. That is the way back from a false positive on a docket no rotation revisits — a denied, dismissed or terminated row has left both rotations, and a granted one leaves the live rotation once no unresolved event remains on it — and it works only while the corrected parse still reads *some* disposition, since a record that now reads undecided is counted `skipped_undecided` and never ingested at all. Dry-run by default; `--stream` narrows to one numbering sequence, which matters because a Term's IFP range runs ~3x its paid one and feeds no scored segment. | `--term` (repeatable), `--stream` (repeatable), `--apply` |
| `refresh-dockets` | Re-snapshot **named** SCOTUS dockets without re-walking their Terms — the targeted counterpart to `refresh-historical`, for when the rows needing a fresh read are known and enumerated rather than a whole population, and re-covering a Term would pay for its entire serial range at ~1 req/s to reach a handful of them. Each `--docket` number is re-served from the supremecourt.gov docket JSON and re-ingested through the walk's own path: identity reconciled by docket number, raw JSON stored as the dated snapshot, the resolved row upserted, filed documents provisioned from `document_floor_term` on. **Corpus-side on the case it exists for**: the write is the shared ingest seam's, so `outcome.json` is recorded only where the event is still open (`record_outcomes` reads open events alone and never overwrites a committed outcome). A docket a walk already landed has its cert event latched resolved, so a re-serve converges the corpus row and leaves the ledger label where it is — moving that is `converge-disposition-labels`' remit. A number the corpus has never held is onboarded outright, ledger included, exactly as a walk would have onboarded it. **Additive exactly as a re-walk is** — the upsert runs through the corpus latches, so no row is deleted and `case_id` never moves, while an *unlatched* column takes the fresh parse, which is the way back from a stale reading on a docket no rotation revisits. **No cursor moves**: a targeted re-read is not a rewind, so the walk resumes where it was and this is safe to run beside a walk of the same Term — both write the same rows through the same latches, and neither can move the other's resume point. The walk's own rules hold, so a named list can never write what a walk would not: a served record with no machine-readable disposition is reported and skipped (pending matters are the forward poller's charter), and one whose case carries an open, predicted event is left to the watchlist so its resolution lands on the evaluate backlog, which `run-evaluate` derives on its own schedule. The list is parsed before the first fetch and a malformed member refuses the whole of it, so a typo costs no upstream traffic and lands no half of a list; the count is bounded by `historical.max_probes_per_run`, and the bound lives in the writer function so a code caller is bounded on the same terms as the command. Applications (`22A123`) and original-docket numbers are separate sequences this path does not serve. Dry-run by default, and the dry run fetches nothing — it resolves each number against the stored rows, so the reading a maintainer takes before a corpus write costs no traffic. `--apply` is a corpus write: run it from the writer lane (`run-seed`'s `refresh_dockets` dispatch input). | `--docket` (repeatable), `--apply` |
| `historical-terms` | Load one capped chunk of the historical per-Term set through the live channel: walk the configured October Terms' docket serials sequentially (persisted per-(Term, stream) cursors, so runs resume) and ingest **every decided petition**, denials included. `refresh-historical` clears those cursors when the pipeline learns to read something the walk did not capture, so past Terms can be re-walked. Ingested petitions land already resolved (label, snapshot, events, OT2021+ documents) and feed the statpack's per-Term base rates and replay/evaluation only; **writes no handoff queues**. The `run-seed` workflow loops it, passing the budget still remaining as `--max-run-seconds` so the final chunk stops itself before the job's hard timeout. | `--report`, `--totals`, `--max-probes`, `--max-run-seconds`, `--summary-out` |
| `discover` | Onboard newly-filed dockets in the tracked courts, advancing each court's watermark (dormant in production: `pull.discover_new_filings` is off — the live channel onboards SCOTUS filings). | `--since`, `--limit` |
| `pull-all` | Refresh the stalest tracked cases within the API budget; write the predict handoff queue, the evaluate queue, and the unrecorded-outcome queue (decided but not deterministically recordable, surfaced on the pipeline-runs dashboard). Only the predict queue becomes a trigger issue. The evaluate queue carries this cycle's fresh resolutions **plus** the **backlog deriver**'s additions — owed gradings re-derived from ledger state (resolved + predicted + unevaluated); only the derived cases are capped by `evaluate.backlog_cases_per_cycle`. Nothing consumes that file as a trigger and no `evaluate_queued_at` stamp is written: it is reported as a count only, since `run-evaluate`'s own scheduled derivation re-derives the same backlog itself; it also holds off a case stamped today, so a pull-window stamp would rotate owed gradings away from the only lane that grades them. | `--limit`, `--out`, `--evaluate-out`, `--unrecorded-out` |
| `live-poll` | One SCOTUS live-channel cycle: probe the Term's docket-number frontier across the paid, IFP, and application numbering streams, onboarding new petitions and applications (persisted per-(Term, stream) cursors) — and, for `live.outgoing_term_grace_days` after the July roll, the outgoing Term from its own cursor so its late tail is caught before the historical walker loses it, re-poll the live watchlist — pending petitions (distributed first, nearest conference first) plus granted dockets retained on their open merits event until judgment, minted at cert-grant detection (see `docs/data-pipeline.md`), re-poll unresolved interim applications (capped at `live.max_applications_per_run`; a changed, still-unresolved substantive application in scope queues predict, daily-debounced — escalation signals latched to the corpus either way), detect resolution from the proceedings text, and write the same three queues as `pull-all` — with predict queued on **distribution transitions** (fresh distribution or relist) of gate-admitted petitions, the cert-calendar predict trigger. The cycle ends with the salience gate's selection pass and its bounded sweep of the petitions the transition trigger missed — the selected ones, plus a deferred case re-admitted to finish an existing predictor cohort, narrowed to that cohort's events (see `docs/salience.md`). | `--term`, `--limit`, `--max-run-seconds`, `--out`, `--evaluate-out`, `--unrecorded-out` |
| `enrich-opinions` | Fill the **cert-granted SCOTUS slice**'s reporter cites and opinion bodies from REST: over the rows carrying `date_cert_granted` and not yet an opinion (`has_opinion` is the idempotency key, so a converged corpus spends nothing), resolve each docket's published opinion cluster — from a stored REST-shaped snapshot's `clusters` links where it has one, else a docket fetch — take the cluster's reporter `citations` and `citation_count`, and take the cluster's first sub-opinion's `plain_text` as the body. The row is written through the corpus's own upsert, per case as it converges (casestore mirror included), which is what lets `has_opinion` derive and `query --full` hydrate the body; a direct `UPDATE` would break the freshness invariant `casestore.read_opinion_text` rests on. Because `has_opinion` latches, a wrong body is permanent, so the pass **refuses rather than guesses**: a docket linking several clusters is skipped, a fetched cluster must name the docket it was reached from, and an opinion whose upstream `type` marks it a separate writing (a concurrence, a dissent) never becomes the body — each counted, with the citations still landing. A stored hyperlink is never fetched as given: a link must resolve under the client's own REST base and name `<resource>/<numeric id>/`, and only the id reaches the client. Three requests a case (two where a REST-shaped snapshot already links the cluster), so `--max-cases` bounds the run's spend ahead of the rate governor, and an exhausted API budget — or a 429 the client's retries could not clear, a quota wall whichever window imposed it — stops the walk cleanly, deferring the cases it did not complete for a re-run in a genuine dead zone; a per-case REST or parse failure is recorded and the walk continues. A granted row whose docket id is the live channel's reserved-range mint addresses nothing upstream, so it is reported `live_only` rather than walked. A no-cluster case is retried on the next run — which is how a grant picks up its opinion the run after publication — so two populations are standing residue at the head of the walk: a grant that never publishes an opinion (a GVR, a DIG), and a decided grant whose docket links no cluster upstream, which is the dominant refusal because the id a granted row carries is its petition-stage docket and the published cluster hangs off it only sometimes. Raise `--max-cases` past them when converging the backlog. Operator-run where the corpus is pulled, `corpus-push` after an `--apply`; it is not a scheduled step, because a schedule wants an ordering the residue cannot sit at the head of, and because the rate governor is per-process it is run outside a pull window. Dry-run by default — the requests are spent either way, so the dry run is how the spend is inspected. Prints an `OpinionEnrichmentResult`. | `--apply`, `--max-cases` |
| `make-fixture-corpus` | Build a tiny deterministic synthetic corpus (cases/events/snapshots across several courts) so the read commands work offline, no remote. | `--out` |

`--limit` / `--max-probes` / `--max-run-seconds` may only *lower* the per-run cap
from `config/`, never raise it, so a run provably stays within budget. The one
exception is `enrich-opinions --max-cases`, which has no `config/` counterpart
and *is* the cap: the pass is operator-run rather than scheduled, so its bound
is set at the call site by whoever is watching the spend.

## Corpus inspection — read the corpus

Read-only views. They read the pulled file by default; where
`--corpus-backend` is listed, `ranged` queries the immutable blob in place on
the corpus remote instead (per-query egress in KBs, read stats echoed to stderr;
see *The ranged read backend* in [data-pipeline.md](data-pipeline.md)).
`query` and `open-events` additionally accept `service` — forward the request
to a `corpus-serve` sidecar (needs `FEDCOURTS_CORPUS_SERVICE_URL`) so the
calling shell holds no cloud credentials; same rows, and `query` prints the
same read-stats line
(see *The corpus query sidecar* in [data-pipeline.md](data-pipeline.md)). The
provisioning commands (`provision-snapshot`, `materialize-event`) additionally
accept `casestore` — read the case's snapshot/documents/event from the per-case
content store rather than the corpus blob (needs `FEDCOURTS_CASESTORE_URL`).
Under the corpus-split mode (`FEDCOURTS_CORPUS_SPLIT=1` — set in production, off
by default for dev environments) those two commands default to `casestore`
without the explicit flag, so the whole fleet reads one store from one setting.

| Command | Purpose | Key flags |
|---------|---------|-----------|
| `corpus-info` | Show the packed corpus location, row count, snapshot count, and a `freshness:` line — the newest `last_pulled` over the cases and the newest stored snapshot date. When the out-of-band pointer override is set, a `pointer:` line follows the freshness line: under `ranged` it names the override's digest (the blob the read actually served), under any other backend it says the override was set but not read — so no vintage is quoted blind against the wrong blob. The committed pointer is a content digest with no date, so this is the cheapest surface that says how old the blob on disk is: the docket pack computes the same `last_pulled` maximum for its `pulled through` line, but only as part of building a pack. A payload-free index reports `no snapshots in this blob` — the snapshots are in the per-case content store, which the snapshot count does not read — and is read on its pull date alone. `--text-coverage` adds the other property worth knowing before quoting a blob — whether its documents carry text at all: over the live-channel SCOTUS rows (the only channel that stores documents) it counts the stored petitions, briefs in opposition, and derived questions-presented rows whose text is empty or whitespace-only, exactly what provisioning stamps on the cell manifest as `empty_text` — written into the cell's manifest, never into a corpus column, so the share has to be counted rather than queried. It is the one read on this command that reaches the content store. The counts stay **per kind** and are never pooled into one total, because emptiness has two causes: on the fetched PDFs it is a scanned filing with no text layer, while an empty derived questions-presented row is as likely to be a capture the deriver would not vouch for over a petition that does carry text (and, since a row is written only where the petition has text, that column is structurally unable to carry a scan — the report says so). Four header lines, each self-limiting, in this order. `text source:` comes **first**, naming the blob's own tables or the per-case content store: every line under it asserts an absence, and a blob-only read of a split corpus finds no documents at all, so the provenance has to be read before the counts. Then `text coverage:`, leading with the **petition** count and share, split into the scans OCR would repair and the PDFs the extractor could not open at all, which it would not; `missing documents:`, the larger failure mode beside it — the cases holding no petition row, over both the stock of distributed cases and the narrower set queued for prediction, which no extraction fix reaches; and `text frame:`, the pass's reach as a bare count, explicitly not a failure rate, since most of the walked slice was never fetched for. The **queued** count holds out the interim application dockets, which are structurally petitionless — an application is not a cert petition, so nothing was ever selected to fetch — and counts them on an indented line under `missing documents:` rather than dropping them, so the excluded floor stays visible; they leave the numerator but stay in its denominator, and the wide distributed count is an unfiltered stock that keeps them entirely. Then the six zero-filled `kind` x `segment` cuts (the salience gate's scored segment — in practice paid against IFP — against the rest of the live slice) and **two** untruncated case-id ledgers: `empty text`, what read back empty and by which kind, and `no petition, queued`, the queued cert cases holding no petition row. Both are enumerated for the same reason: the repair is a per-case question — for the second, which of the provisioning routes a given case missed — and a count names no case. Opt-in and not cheap: it walks the documents of every live-slice case, tens of thousands of rows, which under the split is a content-store manifest round trip each plus a full text body per stored document — taken on a bounded pool of parallel readers, the same one the questions-presented backfill uses — so the default vintage report stays a few KB. The `run-analytics` `text-coverage` mode is the store-configured dispatch for it — the one place the content-store side of the counts is wired — publishing the full report, ledgers included, as a run artifact. | `--corpus-backend`, `--text-coverage` |
| `build-index` | Build the small, payload-stripped **index** beside the corpus (`index.db`): copy the blob, empty the `snapshots`/`documents` tables and NULL `cases.opinion_text` (the bulk that lives in the per-case content store), then `VACUUM`. Keeps every other column (incl. `summary`), events, cursors, and the schema, so it is a drop-in for `statpack`/`backtest`/`query` — proven byte-identical by the parity gate. Under the corpus-split mode the production writer emits this payload-free shape directly; `build-index` converts a legacy full blob to it (and anchors the parity gates). | `--out` |
| `query` | Retrieve relevant priors for a predictor, most relevant first, one JSON row per line. Each row carries the case caption and a derived decade `era` (Term year, else filing/decision date) so relevance is judgeable; `--era` restricts retrieval to one period. `--decided-before` is the back-test replay clock — an exclusive year cutoff keeping only priors that provably precede it (rows with no derivable year are excluded); live forward prediction omits it, and a replay cell reads it from `DECIDED_BEFORE`. The non-cert SCOTUS letter forms (time-extension and unread-ask applications, original-jurisdiction and miscellaneous dockets) are screened out of the returned population — their `granted` is not a cert grant and their days-long turnaround would otherwise dominate the recency ranking — unless `--include-applications`; substantive stay/injunction applications return either way. The surface is **structured filters only** — there is no free-text search argument, and `--era` / `--disposition` are closed vocabularies (an era is a decade token, `1890s`, not a court or a Term). Because a caller that guesses a search engine is the commonest way this surface goes unused, every parse error and both vocabulary refusals print the whole filter vocabulary and a worked invocation beside what was wrong, so the correction can happen in the same session rather than after reading these docs. | `--court`, `--topic`, `--judge`, `--citation`, `--disposition`, `--era`, `--decided-before`, `--include-open`, `--include-applications`, `--limit`, `--full`, `--corpus-backend` |
| `stats` | Aggregate disposition **base-rates** over the corpus — overall, and with `--group-by` a per-group breakdown: court / topic / judge / SCOTUS `term_year` / disposition / `originating_court` / `era`, plus the cert-signal cuts `relist_bucket`, `cvsg`, `fee_class` (paid vs IFP) and `capital_case` (`capital` vs `unmarked`, from the flag supremecourt.gov latches out of its own `bCapitalCase` field OR-ed with the `*** CAPITAL CASE ***` annotation on the docket number — no other channel serves either reading, so a row the live channel never polled buckets as `(unknown)` rather than reading as unmarked), which bucket unparsed and off-form rows as `(unknown)` / `(none)`, and `salience_band` (the active scorer's frozen tiers over the paid modern-cert petitions — the band vocabulary is the version's own). `fedcourts stats --help` renders the same list from the accepted set. Shares `query`'s filter grammar and adds a `--date-from`/`--date-to` filed-date window, a `--term` October-Term filter (SCOTUS only), an `--era` decade filter that also works on rows `--term` cannot parse, and `--cert-stage` for modern Term-prefixed discretionary-cert dockets. `--era` and `--disposition` are the same closed vocabularies `query` refuses an unknown value on, and for a sharper reason here: this command answers a *rate*, so an unrecognized era would return a well-formed report over zero cases rather than visibly nothing. Emits an `AnalyticsReport` JSON on stdout and a Markdown summary on stderr, which `--summary-out` also appends to a file; skips gracefully (exit 0) when the corpus is absent. What the base rates mean and what the prompts anchor on: [metrics/README.md](../metrics/README.md) and [salience.md](salience.md). | `--court`, `--topic`, `--judge`, `--citation`, `--disposition`, `--date-from`, `--date-to`, `--term`, `--era`, `--cert-stage`, `--resolved-only`, `--group-by`, `--summary-out` |
| `open-events` | Print a case's unresolved (predictable) event ids, one per line. | `--court`, `--docket`, `--corpus-backend` |
| `corpus-serve` | Serve `query`/`open-events` over localhost HTTP — the sidecar behind the `service` backend. Holds the one corpus connection (and, on `ranged`, the cloud credentials from its own environment) so callers query credential-free; `/healthz` runs a real point read, so green means the corpus is answerable (on `ranged`, the payload and the sidecar log carry the check's own GET/byte counters). Runs until interrupted. Local recipe: `corpus-serve --corpus-backend local`, then `FEDCOURTS_CORPUS_BACKEND=service FEDCOURTS_CORPUS_SERVICE_URL=http://127.0.0.1:8377 fedcourts query …`. | `--corpus-backend`, `--host`, `--port` |
| `conference-set` | The pending-before-conference set: every pending modern-cert petition with a parsed "DISTRIBUTED for Conference of …" membership, grouped by conference date — the live cert watchlist the September long-conference report reads off. `--out` also writes the per-petition JSON. | `--out` |
| `live-frontier` | Snapshot the live cert watchlist's readiness for the ops dashboard: watchlist size, the distribution calendar with the next conference relative to `--today`, and how many watchlist petitions carry provisioned filed-document text. Produced where the corpus is pulled and published to the `ops-metrics` branch (the corpus-writer path) so the corpus-free `run-ops` presenter can render it. Emits a `LiveFrontier`; skips gracefully when the corpus is absent. | `--out`, `--today` |
| `provision-snapshot` | Materialize a case's corpus snapshot to disk for an agent run — plus any stored filed-document text (petition, questions presented, brief in opposition — fetched pipeline-side by the live poller) under `record/documents/` with a `documents.json` manifest, and the cell's mode context (`record/context.json`). **Which** snapshot is the moment's question, not the corpus's: on by default, `--moment-cutoff` places a forward cell at the information set its `--event` declares — everything filed strictly before the day after that event opened — so a grant-moment merits cell is not handed the merits calendar entries (briefs filed, amici filed, the case argued) that only the *briefed* moment declares. The snapshot is then the one the docket really served at the moment where the corpus kept one (`snapshot_provenance` `dated`; taken only where it reaches the trigger day, since `snapshot_at` is bounded above by the cutoff and not below, and a snapshot from well before the moment would place the cell earlier than the cohort it is filed under), otherwise the latest payload with its post-cutoff entries removed and its date set to the cutoff (`truncated`). The cut is on the dated proceedings, the documents (on `entry_date`, falling back to `fetched_at` — safe in one direction only, since a fetch cannot precede a filing), and the date-keyed top-level fields (`date_argued` and siblings, dropped when they fall on or after the cutoff or cannot be parsed; the generation stamp always, since it dates the pull rather than the docket). Undated counsel/amici blocks are as at the pull, carried by `truncated` cells only — a `dated` cell has a genuine point-in-time payload with none of the residual. Because the two arms therefore differ in what survived, a figure over placed cells owes the `dated`/`truncated` counts beside it ([metrics/README.md](../metrics/README.md)). The counts of what each cut removed are echoed to the run log, not written to `context.json` — the cell reads that file, and the size of a cut is itself a signal. `context.cutoff` records where, and is the cohort marker separating a placed cell from one reading simply the latest snapshot (`as-stored`) — which is what a cell with no `--event` gets (the evaluate path), an `--event` naming no declared moment (an entry-pinned event), a declared moment whose corpus row records no opening date, the cert petition baseline (its opening date is docketing, not the distribution its moment declares — the exception is that one moment, not the cert stage: the `cvsg` and `arrival` moments are placed, as is the interim application baseline, whose declared moment *is* arrival), and what `--no-moment-cutoff` forces. The staleness bound and the textual scan below both run on the **latest** payload, before any cut: a disposition filed after the cutoff is exactly what a cut would hide. `--refuse-terminal` (the forward predict path) refuses a forward cell — exit 3, nothing written — through three gates, mechanical before textual: the **record gate** (`store.forward_refusal_reason`: a committed `outcome.json`, the corpus event's `resolved` flag, or the row's latched outcome for the event's stage — the merits judgment for a merits moment, the disposition/resolution date otherwise, applied to the case baseline when `--event` is omitted; under the casestore backend — the `--corpus-backend` flag, or the corpus-split default the production fleet provisions under — the source exposes events but no rows, so the row-level half consults the corpus index through the ordinary read backend (ranged in the cell workflows, whose provisioning step carries the index credentials beside the casestore URL); when no index is reachable the event-keyed checks still gate the cell and the skipped half is a spoken warning), the **staleness gate** (`--max-snapshot-age-days`, 0 = off and the default; `run-predict` arms it at 10 days: a pre-pause snapshot discloses nothing about what happened during the pause, so age itself is disqualifying), and the **textual scan** over the snapshot: on the merits event a parsed merits judgment (the cert grant that opened the event is its legitimate record); on every other event any entry reading terminal, any entry carrying a machine-readable disposition order, or — on an application docket — a legible interim disposal. A forward prediction on a decided event would be a mislabeled back-test. | `--court`, `--docket`, `--event`, `--out`, `--mode`, `--moment-cutoff`, `--refuse-terminal`, `--max-snapshot-age-days`, `--corpus-backend` |
| `assert-cell-record` | Assert that a cell's provisioned record landed complete — the check `run-predict` runs between provisioning and any token spend. Complete means both halves of the provisioning write are on disk and readable: `record/context.json` parses as a `PredictionContext`, and the dated snapshot that context names is present, non-empty, and parses as JSON — parsed rather than counted, because the provisioning write is not atomic and a half-landed one leaves a truncated file a size check would pass. Exit 0 complete; exit 1 incomplete, with a `::warning::` naming the missing half, which the workflow turns into the same cell refusal an exit-3 forward-gate refusal gets. The provisioned snapshot is every predictor's guaranteed-common input, so a cell whose record never landed would forecast from base rates alone while its output claimed the shared baseline — and provisioning's exit code cannot see a read that half-lands, which is why this asks the disk. Purely local: it reads no corpus and holds no credential, and it checks the default record paths only (a `provision-snapshot --out` written elsewhere is not what it asserts). | `--court`, `--docket`, `--event` |
| `corpus-integration-check` | Run the fixed read set the `integration-test` workflow's ranged-reads scenario dispatches — a point lookup (open events), a priors retrieval, a snapshot provisioning — each on its own connection so a ranged run reports per-read GET/byte counters. With `--corpus-backend service` (the corpus-service scenario) the set runs through the sidecar client instead — query, open-events, and the full-query hydration probe, which fails when an opinion-bearing prior hydrates an empty body (a corpus with no opinion-bearing row passes with an explicit UNVERIFIED note). Emits the machine report JSON on stdout and a Markdown summary on stderr; `--summary-out` also appends the summary. Exits non-zero on any empty read or a blown wall-clock budget. | `--court`, `--docket`, `--limit`, `--budget-seconds`, `--snapshot-out`, `--summary-out`, `--corpus-backend` |
| `corpus-integration-case` | Resolve a case `corpus-integration-check` and the cell scenarios can run against, out of whichever corpus the run actually holds — a static default cannot serve, since each deployment environment resolves its own corpus pair (a case named in one is absent from another) and any one case drifts out of shape as its docket resolves. Returns the first case that is **snapshot-bearing** (the blob stores a snapshot — the input `provision-snapshot` needs), **in predict scope** (`out_of_scope_reason_full`, so the snapshot-aware rules apply, not just the `predict_excluded` latch), and **still predictable** — that last asked of the consumer's own gate, `store.forward_refusal_reason_from_parts` at the case baseline, which is what `provision-snapshot --refuse-terminal` runs in the cascade leg. Asking the real gate rather than approximating it is the point: it refuses on a latched *resolution date* as well as a disposition, so a cert-granted petition awaiting merits judgment — undisposed to a naive filter — is never handed over. ## Corpus transport — move the blob, and copy a slice of both stores

The pull/push pair the data workflows (and a developer with credentials) use to
move the corpus index blob between disk and the S3 remote; both read the remote
URL from `CORPUS_REMOTE_URL` (legacy `DVC_REMOTE_URL` accepted). The seeder
below moves a *slice* of both stores onto a second, non-production pair, and
names its source **and** its destinations explicitly rather than reading
either from that variable — the pinned source is what it refuses to write to.

| Command | Purpose | Key flags |
|---------|---------|-----------|
| `corpus-pull` | Download the blob the pointer the read paths resolve names — the out-of-band override when set, else the committed `corpus/corpus.db.ref` — verifying its checksum + size before the file lands. `--missing-pointer` governs only the committed file, so it is inert while the override is set. Every pull records the resolved pointer in a gitignored sidecar beside the blob, which is how `corpus-info` flags a blob on disk that is not the committed ref's. | `--missing-pointer fail\|warn` |
| `corpus-push` | Digest the local blob, upload it to its content-addressed key (put-if-absent; the remote stays add-only), and rewrite the pointer — blob before pointer, so a committed pointer always resolves. Refuses to run while the out-of-band pointer override is set: a writer owns the committed pointer. | |
| `corpus-seed-slice` | Copy a named docket slice into a **staging corpus** — its own bucket/prefix pair, so orchestration and the read/write seams get live end-to-end verification without anything gaining write access to production. Builds the two halves a split-mode corpus has: a payload-free index blob carrying only the slice's `cases` and `events` rows (rebuilt through the corpus's own upsert seams, so it is schema-current whatever the source's vintage; the opinion body is dropped and no snapshot or document row is written, so the slice has split-on parity whatever mode the seeding process runs under) published to `--dest-remote` at its content-addressed key exactly as `corpus-push` publishes production's, and a **key-level copy** of every content-store object under each case's prefix into `--dest-casestore` — the writers' own bytes, not a re-serialization, so every dated snapshot and content-addressed document leaf arrives unchanged. Objects are copied *before* the blob is published, so a reader resolving the new pointer always finds the payloads its rows refer to; within a case the documents manifest lands *after* the leaves it names, the same rule one level down. The store's two kinds of object are copied on different rules, and the distinction is load-bearing: write-once keys (dated snapshots, content-addressed leaves) the destination already holds are skipped, while the three **mutable** manifests the writers overwrite in place (`case.json`, `events.json`, `documents/documents.json`) are re-copied every apply — skipping those would leave a re-seeded staging store describing a case the source has moved past, its manifest naming a superseded filing while the blob half, rebuilt from scratch each time, says otherwise. Provisioning the stores, the variables, and the role is the maintainer runbook in [security.md](security.md). | `--source-remote`, `--source-casestore`, `--dest-remote`, `--dest-casestore`, `--dockets`, `--dockets-file`, `--apply`, `--max-cases`, `--stage-db`, `--summary-out` |

It is an in-place *recompute* of harness-owned fields, not the re-grade the leaderboard's collapse counts — that sense mints a second `evaluation.json` from a new evaluator run, which is the route for a changed judgment and the wrong one for a corrected outcome. The recomputed claim block and skill fields are pooled from the statpack committed *now*, so re-grade a whole cohort against one pack. Re-grade **every** evaluator on the event: `validate`'s `evaluation_correct_agrees` collapses to the latest runs and requires them to agree, so a partial re-grade fails the ledger, which is the check working (it reaches the `correct` bit only, and only where two or more evaluators graded the cell — see [metrics/README.md](../metrics/README.md)). One divergence `--regrade` cannot converge: gradings that straddle a re-prediction each preserve their own `prediction_run_id`, so the repair there is the ordinary re-stamp, taken promptly and with its stated cost — it re-resolves the identity to the latest prediction and rewrites `process_version`. Every `--regrade` refusal is judged before the first write, so none can leave an event half corrected, and each target's process scope (`frozen` / `alpha`) is echoed as it goes — the operation leaves no `superseded_gradings` trace, so that line is the record of a claimable cell moving. ## Maintenance — corpus-informed cleanup

Deterministic sweeps that prune or converge already-merged derived artifacts the
append-only writers can never fix. All need a pulled corpus (`fedcourts
corpus-pull`), and they land through two channels, named by where the applied
result lands. The **maintainer-reviewed** sweep —
`cleanup-out-of-scope-predictions` — runs from a dev checkout, and a
maintainer lands the result as a **reviewed** (not auto-merged, manually
merged) PR on a `cleanup/*` branch. The **writer-lane** sweeps —
`reconcile-scope`, `dedupe-live-rows`,
`relabel-application-events`, `backfill-merits-judgments`,
`backfill-event-moments`, `backfill-merits-events`, the attribution
repairs `remove-unmintable-events` and `reopen-misattributed-outcomes`, and
`scrub-bulk-cluster-fields` — run
in run-seed's writer lane on its schedule, with a dry run from a dev checkout
available for inspection. What both channels share is why neither is a
collect commit: a destructive change to the ledger is a shape no collect
jail admits, so it lands either behind a maintainer's review or in the
writer lane's one pointer commit — atomic with the corpus it must match,
and bounded there by each repair's per-run blast-radius cap. The remaining
entries name their own channel.

Rows already sharing a normalized identity with another row are reported as a count and still repaired: the rewrite neither creates that collision nor resolves it (it is the dedupe pass's population, visible to it either way), so withholding the repair would strand the marking for no gain. That count is SCOTUS-scoped, because the two-channel identity reconciliation it belongs to is — a marked circuit row is repaired but never reported as sharing. `capital_case` is raised rather than assigned a computed value, sitting in the upsert's max-latch family, so a flag another channel set stays set and the write can only advance it. ## Local iteration — the full cascade off Actions

`local-cascade` is the repeatable, local form of the "one full cascade proven"
milestone: it drives a single case through the whole derived-artifact pipeline —
**provision → predict → evaluate → validate** — without GitHub Actions, the
iteration loop that otherwise only runs inside `run-predict` / `run-evaluate`. It
reuses the production seams (the engine-runner, the predictor/evaluator
registries, the packed corpus) so a green local run faithfully predicts a green
CI run.

| Command | Purpose | Key flags |
|---------|---------|-----------|
| `local-cascade` | Provision a case's snapshot, predict it with every enabled predictor (`--predictor` narrows to one — the one-cell shape a token-spending smoke run wants), evaluate the resulting predictions with every enabled evaluator, and validate the produced ledger. `--require-predictions` fails the run when no predictor cell wrote a prediction — a real agent that finishes blocked exits 0 with a validly-empty ledger, which a smoke must treat as failure. | `--court`, `--docket`, `--event`, `--engine`, `--run-id`, `--predictor`, `--corpus-backend`, `--require-predictions` |

It reads the case from the packed corpus — point it at the synthetic fixture
(`make-fixture-corpus`) for a fully offline run, a real `corpus-pull`-provisioned
one, or (via the corpus-backend setting) the blob in place on the corpus remote.
`--corpus-backend` overrides that setting for the cascade's *own* provisioning
reads only (`local` or `ranged` — the query sidecar's `service` surface does not
serve them); the spawned agent still inherits the ambient corpus settings, so an
environment configured for the sidecar drives the agent's retrieval through it
while provisioning reads the blob directly — the split the `integration-test`
workflow's engine-smoke scenario runs on.
With no `--event` it runs every event the case defines; a resolved event also
gets its ground-truth `outcome.json` materialized so the evaluate stage has
something to score. The derived artifacts land under `data/` exactly as a real run
would — **review and discard them**, don't commit a local cascade's output.

**Engines.** `--engine` selects the backend for every cell:

- `stub` (default) — the deterministic, offline, token-free reference engine.
  This is the acceptance path: valid artifacts end to end with no network.
- `replay` — also offline, but emits a **captured real prediction** from the
  cassette at `FEDCOURTS_REPLAY_ROOT` (a committed recording under `tests/cassettes`)
  instead of the stub's trivial floor. The recorded forecast carries a real
  probability and panel votes, so the scoring metrics and leaderboard roll-up run
  over realistic output; identity fields are rebound to each cell. Set
  `FEDCOURTS_REPLAY_ROOT` or the command errors clearly.
- `claude-code` / `codex` / `gemini` — drive the **real** headless agents
  (`claude`, `codex`, `gemini`) over the same cell contract the workflows use
  (the inline-identifier kickoff prompt plus the env vars), so the cells are
  byte-identical in shape to a CI run. The `claude` CLI ships in the devcontainer
  (`codex` you install yourself; `gemini` is `npm install`-ed, as the workflow
  does).

**Auth for the real engines.** Credentials are inherited from the environment,
never assembled by the command. For Claude, set either:

- `ANTHROPIC_API_KEY` — pay-per-token, exactly as CI meters automated inference; or
- `CLAUDE_CODE_OAUTH_TOKEN` — the **subscription** OAuth token from
  `claude setup-token`, so local iteration draws on your Claude subscription
  instead of billing per token. This mirrors the `claude_code_oauth_token` fallback
  noted in `run-predict.yml`.

For Codex, set `OPENAI_API_KEY`. The pinned codex CLI never reads that
variable itself, so the runner feeds it to `codex login --with-api-key`
(over stdin) before each cell — into a run-scoped temp `CODEX_HOME`, so your
`~/.codex` subscription login is never touched; unset the variable to use an
existing `codex login` instead, and an explicitly exported `CODEX_HOME` wins
over the run-scoped default. For Gemini, set `GEMINI_API_KEY`.
